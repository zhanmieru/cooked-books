# CookedBooks

RL-среда для дообучения ИИ-аудитора. Генератор создаёт книги вымышленной компании, вносит в них известные ошибки и записывает каждую правку. Агент видит книги только через пять инструментов и сдаёт найденные ошибки с доказательствами. Оценщик сверяет ответ с эталоном и считает награду.

Работа для Genesis Hackathon 2026, трек FinTech.

Название: cooking the books по-английски значит «подделывать отчётность». Здесь книги «приготовлены» нарочно и по записанному рецепту, поэтому каждая ошибка в них известна и доказуема.

Все компании, клиенты, суммы и курсы вымышлены. Сеть, платные API и GPU не нужны.

## Проверка одной командой

Нужен только Docker.

```bash
make verify
```

Команда собирает образ с отключённой сетью и запускает всю проверку в контейнере: без сети, 2 ядра, 4 ГБ памяти, файловая система только для чтения. В конце печатается таблица по блокам жюри, тот же текст пишется в `reports/verify_report.md`. Код выхода равен 0, только если прошли все тесты.

Что печатает последняя версия, сокращённо (1 701 тест, около 6 минут на двух ядрах):

```
| Block | Jury checks | Result |
|---|---|---|
| 1. Contract and isolation | C01-C20 | 20/20 |
| 2. Data and ground truth | D01-D20 | 20/20 |
| 3. Matcher and reward | tests 1-20 (R01-R20) | 20/20 |
|  | examples M01-M12 | 12/12 |
| 4. Reproducibility | P01-P20 | 20/20 |

Generator attempts rejected by the verifier: 0 of 2708 (2708 episodes accepted).
Verdict: PASS
```

На каждую проверку из опубликованных определений жюри есть тест с её номером: `tests/jury/test_block1_contract.py` (C01–C20), `test_block2_data.py` (D01–D20), `test_block3_reward.py` (тесты 1–20 и примеры M01–M12), `test_block4_pairs.py` (P01–P20).

Подробности запуска:

- При первом запуске Docker один раз скачивает базовый образ `python:3.11.18-slim-trixie`, закреплённый по digest (около 48 МБ). Дальше сеть не нужна: зависимости ставятся из `vendor/wheels/`.
- На macOS с Colima сначала `colima start --cpus 2 --memory 4`.
- Без `make` то же самое делают две команды:
  ```bash
  docker build --network none -t cookedbooks-verify:local .
  ```
  ```bash
  docker run --rm --network none --cpus 2 --memory 4g --read-only --tmpfs /tmp cookedbooks-verify:local
  ```
- Без Docker: Python 3.11, `pip install -r requirements.lock`, затем `python -m cookedbooks.verify` из корня репозитория.
- Остальные цели: `make help`.

## Как жюри подключается: `judge_adapter.py`

Файл лежит в корне репозитория. В контейнере рабочая папка — `/app`, адаптер импортируется оттуда: `import judge_adapter`. Интерактивная оболочка в том же контейнере без сети: `make shell`.

```python
def generate_episode(seed: int, config: dict, output_dir: str) -> None
def make_env()                     # объект с reset(seed, config) и step(action)
def score_episode(episode_dir: str, findings: dict, inspection_steps: int) -> dict
```

| Функция | Что делает |
|---|---|
| `generate_episode` | Пишет в `output_dir` восемь файлов эпизода. `config` — настройки генератора (`team_config`); обёртка `{"team_config": {...}}` тоже принимается. После генерации эпизод проверяет независимый проверяющий; при отказе генерация повторяется, не больше 20 раз |
| `make_env().reset` | `config = {"mode": "closed" \| "train", "episode_dir": "...", "team_config": {...}}`. С `episode_dir` загружается именно эта папка: ничего не генерируется, ID не меняются. Без неё, только в `train`, эпизод создаёт генератор из `seed` и `team_config` |
| `make_env().step` | Действие `{"name": "...", "args": {...}}`, ответ `(observation, reward, terminated, truncated, info)` |
| `score_episode` | Читает `truth.json` и возвращает `{"tp", "fp", "fn", "precision", "recall", "f1", "return"}`. Для неверной структуры ответа: `return = -1`, остальные поля `null`, запись в журнале оценщика |

Короткий пример:

```python
import judge_adapter

judge_adapter.generate_episode(7, {"errors": {"duplicate_invoice": 1}}, "/tmp/ep")
env = judge_adapter.make_env()
obs, info = env.reset(7, {"mode": "closed", "episode_dir": "/tmp/ep", "team_config": {}})
obs, reward, terminated, truncated, info = env.step(
    {"name": "list_records", "args": {"table": "invoices", "cursor": None, "limit": 50}})
```

### Наблюдения и результаты

| Что | Форма |
|---|---|
| Первое наблюдение | `{"task": str, "manifest": object, "policy": object, "remaining_steps": 100}` |
| Остальные | `{"result": ..., "error": null \| {"code", "message"}, "remaining_steps": int}` |
| `list_records(table, cursor, limit)` | `{"records": [...], "next_cursor": null \| str}`; таблицы `ledger`, `invoices`, `payments`, `fx`; первый `cursor` — `null`; на странице не больше 50 записей |
| `get_record(table, id)` | объект записи. `ledger` — по `row_id`; `invoices` и `payments` — по `doc_id`, а если такого нет, по `invoice_id` или `payment_id`; `fx` — по ключу `date:SRC:TGT` |
| `get_document(doc_id)` | объект счёта или платежа |
| `calculator(expression)` | десятичная строка: `0.1+0.2` → `"0.3"`. Только арифметика, ничего не исполняется |
| `submit(findings)` | только `{"accepted": true}` или ошибка структуры. Правильность ответа не сообщается |

Коды ошибок: `unknown_action`, `unknown_table`, `unknown_id`, `bad_arguments`, `calc_error`, `invalid_submission`, `time_limit`, `episode_over`. Текст ошибки короткий и постоянный, без путей и закрытых данных. Любое действие, в том числе ошибочное, тратит один шаг.

Поле `task` — это полный свод правил на английском, около 8 000 символов. Его и открытых записей достаточно, чтобы решить любой эпизод.

### Режимы и границы

- `closed`: среда вообще не открывает `truth.json` и `provenance.json`; награда политике всегда равна числу 0, `info` пуст. Настоящую награду считает `score_episode`.
- `train`: на последнем шаге политика получает итоговую награду и метрики в `info`.
- 100 действий на эпизод, считая `submit`. `submit` сотым действием принимается. Сотое действие без `submit` даёт `truncated = true`, ответ считается пустым.
- 60 секунд от входа в `reset`. Действие после лимита возвращает `time_limit` и `truncated = true`. Для воспроизводимой проверки лимит можно уменьшить: `team_config.time_limit_s`.
- Любой `submit` завершает эпизод. После конца эпизода действия ничего не меняют.

## Четыре типа ошибок

Точное значение `type` в ответе и в эталоне:

| Наш `type` | Тип ошибки в кейсе | Виды | `affected_ids` | Сумма и валюта | Набор доказательств |
|---|---|---|---|---|---|
| `duplicate_invoice` | дубль счёта | — | `doc_id` обоих счетов | `total_minor`, валюта счёта | оба `doc_id` |
| `unallocated_payment` | пропущенное или частичное распределение платежа | `missing`, `partial` | `doc_id` платежа и `doc_id` счёта | нераспределённый остаток, валюта платежа | оба `doc_id` |
| `fx_error` | неверная дата или курс конвертации | `wrong_date`, `wrong_pair` | `doc_id` счёта | модуль разницы, базовая валюта | `doc_id` счёта, `row_id` строки `REVENUE`, ключ правильного курса |
| `cutoff_error` | ошибка отнесения к отчётному периоду | `late`, `early` | `doc_id` счёта | `total_minor`, валюта счёта | `doc_id` счёта и `row_id` строки `AR`; либо `doc_id` и `row_id` строки `REVENUE` |

Два сценария со взаимодействием:

- **S1.** Валютный счёт у границы периода пересчитан по курсу не той даты, а его платёж распределён частично. Две ошибки на одном счёте: `fx_error` и `unallocated_payment`.
- **S2.** Дубль валютного счёта, копия проведена по курсу другой даты. Две ошибки: `duplicate_invoice` на обоих счетах и `fx_error` на копии.

Рядом с ошибками в книгах есть корректные двойники: ежемесячные счета на одну сумму, платёж частями, настоящий аванс, переплата, возврат после двойной оплаты, счёт около полуночи или границы периода, счёт в день без курса. Правило для каждой ошибки и её двойники описаны в [DESIGN.md](DESIGN.md), раздел 5.

## Файлы эпизода и история изменений

Одна папка, восемь файлов: открытые `manifest.json`, `ledger.csv`, `invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json` и закрытые `truth.json`, `provenance.json`. Форматы соответствуют разделу 03 кейса: время в ISO-8601 со смещением, деньги в целых минимальных единицах, курсы десятичными строками, отсутствующие ссылки явным `null`. Точные схемы — [EVALUATION_CONTRACT.md](EVALUATION_CONTRACT.md), раздел 2.

Наши дополнительные поля: в счёте `po_ref` (номер заказа) и `service_period` (месяц услуги); в манифесте `utc_offset`, `record_counts`, `document_count`, `currency_exponents`. Эталон они не раскрывают.

`provenance.json` хранит для каждой внесённой ошибки обратимую правку: какие записи добавлены, изменены или удалены, целиком «до» и «после», и какую контрольную проверку правка нарушает. Чтобы получить книги до ошибок, нужно пройти правки с конца и применить обратные. Это делает независимый проверяющий:

```bash
python -m cookedbooks.verifier episodes/dev/dev-08
```

Он откатывает правки, проверяет шесть контрольных проверок на чистых книгах, сам ищет ошибки по открытым файлам, сверяет их с `truth.json` и проверяет достаточность каждого набора доказательств. Проверяющий написан по [DESIGN.md](DESIGN.md) отдельно от генератора и его код не импортирует.

### Одна ошибка на одном экране

```bash
python -m cookedbooks.xray episodes/dev/dev-03 --issue ISS-0001
```

Команда показывает одну внесённую ошибку целиком, в трёх частях:

1. **Цепочка доказательств.** Записи из `affected_ids` и из набора доказательств, под каждым документом его проводки. Отмечено, какие записи добавила или изменила ошибка.
2. **До и после.** Что именно изменила правка, по данным `provenance.json`.
3. **Двойник.** Законная операция из того же эпизода, похожая на эту ошибку, и причина, по которой она не ошибка.

## Поля с идентификаторами

Для согласованной замены ID в копии эпизода:

| Пространство ID | Где определяется | Где встречается как ссылка |
|---|---|---|
| `row_id` | `ledger.csv` | `truth.evidence_sets`; в `provenance.json` — `key` и записи `before`/`after` |
| `doc_id` | `invoices.jsonl`, `payments.jsonl` | `truth.affected_ids`, `truth.evidence_sets`; в `provenance.json` — `key`, `distractors[].ids`, `before`/`after` |
| `invoice_id` | `invoices.jsonl` | `ledger.invoice_id`, `payments.invoice_refs`, `before`/`after` |
| `payment_id` | `payments.jsonl` | `ledger.payment_id`, `before`/`after` |
| `entity_id` | отдельно не определяется | `invoices.entity_id`, `ledger.entity_id`, `before`/`after` |
| `issue_id` | `truth.json` | `provenance.injections[].issue_ids` |

Не являются ID и не заменяются: ключ курса `date:SRC:TGT`, `episode_id`, `po_ref`, `service_period`, названия счетов учёта, коды валют. Переставлять можно строки всех четырёх таблиц; порядок `line_items` внутри счёта менять нельзя. Если в `fx.csv` повторится ключ, второе и следующие вхождения получают суффикс `#2`, `#3` по порядку строк; генератор повторов не создаёт.

Наш инструмент делает такую копию сам:

```bash
python -m cookedbooks.verify.transform episodes/dev/dev-08 /tmp/dev-08-copy --permute --relabel --style hex
```

Ограничение: ID из разных пространств не должны совпадать между собой, подробнее в разделе «Ограничения».

## Сопоставление и награда

Код: `cookedbooks/findings.py` (структура ответа) и `cookedbooks/grader/` (сопоставление, метрики, награда). Правила целиком — [EVALUATION_CONTRACT.md](EVALUATION_CONTRACT.md), разделы 4–6. Коротко:

- Сначала проверяются структура и размеры, потом нормализуются множества. Больше 30 выводов, больше 10 ID доказательств в выводе (считая повторы), объяснение длиннее 1 000 символов Unicode, сумма не целым числом — неверная структура, награда −1.
- Вывод подходит к ошибке, если совпали `type`, множество `affected_ids`, `currency`, сумма в пределах допуска, а `evidence_ids` содержит целиком хотя бы один допустимый набор и не содержит несуществующих ID. Строки сравниваются точно.
- Допуск суммы по умолчанию 0 для всех типов. Изменить его можно только заранее, ключом `amount_tolerance_minor` в `policy.json`.
- Берётся паросочетание наибольшего размера. Среди равных выбор детерминирован: ошибки по `issue_id`, для каждой наименьший индекс вывода.
- `return = clip(2*F1 - 1 - 0.002*inspection_steps, -1, 1)`. Метрики считаются в точных дробях.
- Неизвестный `type`, чужая валюта, несуществующие ID — обычный промах (FP), а не ошибка структуры.

## Базовые политики и траектории

Каждая политика запускается отдельным процессом, который получает только наблюдения:

```bash
python -m cookedbooks.runner.run --policy simple_recon --episode episodes/dev/dev-05 --mode closed
```

В дочерний процесс копируются только файлы самих политик; оценщика, генератора и проверяющего там нет. Обмен идёт строками JSON через stdin и stdout.

Диагностика на проверочных эпизодах в закрытом режиме (`make baselines`):

| Политика | Точность | Полнота | F1 | Награда | Шагов |
|---|---|---|---|---|---|
| `random_explorer` | 0,000 | 0,000 | 0,000 | −1,000 | 16,2 |
| `simple_recon` | 0,340 | 0,567 | 0,412 | −0,202 | 17,6 |
| `flag_all` | 0,000 | 0,000 | 0,000 | −1,000 | 3,0 |
| `oracle` | 0,800 | 0,800 | 1,000 | +1,000 | 0,0 |
| `evidence_solver` | 0,800 | 0,800 | 1,000 | +0,958 | 21,2 |

Это диагностика скриптовых политик, а не заявление об обучении: веса моделей не обучались. Точность и полнота усреднены по эпизодам. На чистых книгах пустой ответ по правилам кейса даёт P = R = 0 при F1 = 1, поэтому при двух чистых эпизодах из десяти даже идеальная политика показывает 0,8.

`trajectories.jsonl` — 546 шагов: пять политик на десяти обучающих эпизодах в режиме `train`. Поля каждой записи: `episode_id`, `step`, `action`, `observation`, `reward`, `terminated`, `truncated`, а также `policy` и `split`. Тесты проверяют, что повтор записанных действий воспроизводит каждое наблюдение и награду и что в наблюдениях нет данных эталона. Действия политики `oracle` содержат верный ответ по построению: она получает его от запускающей стороны.

Открытые эпизоды и траектории пересобираются командами `make episodes` и `make trajectories`; тесты сравнивают лежащие в репозитории файлы со свежей сборкой.

## Чем подтверждена корректность, кроме тестов жюри

- **Три независимые реализации правил.** Генератор, проверяющий и политика `evidence_solver` написаны отдельно, по тексту правил, без доступа к коду друг друга. Проверяющий согласен с генератором на всех проверенных эпизодах, их больше 35 000. Решатель, который читает книги только через инструменты, на 6 000 эпизодов нашёл все ошибки без ложных тревог.
- **Атаки на награду.** `python -m cookedbooks.verify.attacks` гоняет 72 вида атак на настоящих эпизодах: повторы, подбор сумм и валют, чужие и лишние доказательства, обвинение двойников, «всё, кроме решения», текст-инъекции в объяснении, неверные типы полей, повторная отправка, действия после конца, попытки прочитать закрытые файлы. Ни одна не набирает больше oracle при том же числе шагов.
- **Зонд простых трюков.** `python -m cookedbooks.verify.shortcuts` измеряет, насколько простой признак записи (позиция в файле, вид ID, размер клиента, время суток, форма платежа) предсказывает ошибку.

## Ограничения

| Ограничение | Где это видно |
|---|---|
| Платёж всегда в валюте счёта; курсовые разницы при оплате не моделируются | любой эпизод с иностранной валютой |
| Часовые пояса — постоянные смещения, без летнего времени | `manifest.utc_offset` |
| Только продажи; закупок с документами нет | фоновые проводки без документов |
| Дубль — точное совпадение ключа обязательства; дублей с опечатками нет | рецепты D06–D08 |
| Вне сценариев S1 и S2 ошибки не пересекаются на одном документе | рецепты D06–D15 |
| Ошибка «курс не той пары» находится одной сверкой проведённого курса с таблицей; двойника у неё нет | зонд простых трюков; `docs/failures.md`, F-03 |
| ID в ответе — строка без указания таблицы. Если при замене ID записи из разных таблиц получат одну строку, поиск по номеру счёта и различимость доказательств ломаются. Ответ oracle оценивается одинаково и в этом случае | `tests/integration/test_known_limits.py`; F-05 |
| Честное полное чтение книг стоит от 12 до 63 действий, поэтому потолок награды для агента без подсказок — от 0,874 до 0,976 | строка `evidence_solver` в таблице политик |
| Процесс политики ограничен средствами Python, а не операционной системы; полную изоляцию даёт контейнер | [DESIGN.md](DESIGN.md), раздел 8 |
| Веса моделей не обучались. Награда не доказывает пригодность агента для настоящего аудита | — |

## Воспроизводимость

- Одинаковые `seed` и настройки дают побайтно одинаковые файлы эпизода; тест сравнивает открытые эпизоды в репозитории со свежей генерацией.
- Деньги — целые числа, курсы и метрики — точные дроби. Чисел с плавающей точкой в расчётах нет.
- Версии: Python 3.11, зависимости в `requirements.lock` (только `pytest` и `hypothesis` для тестов; сама среда работает на стандартной библиотеке), базовый образ закреплён по digest, версия генератора и номер попытки записаны в `provenance.json`, версия схемы — в `manifest.json`.
- Колёса зависимостей универсальные (`py3-none-any`), поэтому образ собирается и на x86, и на ARM.
- Случайные тесты идут по закреплённому набору примеров.
