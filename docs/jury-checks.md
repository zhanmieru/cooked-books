## 1. Как жюри подключается: `judge_adapter.py`

Файл лежит в нашем контейнере. Жюри импортирует его и вызывает три функции:

```python
def generate_episode(seed: int, config: dict, output_dir: str) -> None: ...
def make_env(): ...   # объект с reset(seed, config) и step(action)
def score_episode(episode_dir: str, findings: dict, inspection_steps: int) -> dict: ...
```

- **`generate_episode`** пишет в папку жюри весь эпизод: `manifest.json`, `ledger.csv`, `invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json` и закрытые `truth.json`, `provenance.json`. Это обёртка над нашим генератором.
- **`reset(seed, config)`** получает `config = {"mode": "closed", "episode_dir": "<папка>", "team_config": {...}}`. В этом случае среда загружает именно эту папку: ничего не генерирует заново и не меняет ID. Повторный `reset` начинает тот же эпизод сначала. Для открытого режима `mode = "train"`; если `episode_dir` нет, эпизод создаёт наш генератор из `seed` и `team_config`.
- **`step(action)`** получает `{"name": "<действие>", "args": {...}}`. Имена: `list_records`, `get_record`, `get_document`, `calculator`, `submit`. Аргументы: `table, cursor, limit` (первый `cursor` равен `null`); `table, id`; `doc_id`; `expression`; `findings` (объект findings.json из §05 кейса).
- **`score_episode`** для корректного `submit` возвращает `{"tp", "fp", "fn", "precision", "recall", "f1", "return"}`. Для некорректной структуры: `return = -1`, остальные поля `null`, ошибка в журнале оценщика.
- Канонические имена таблиц: `ledger`, `invoices`, `payments`, `fx`. Поля записей — как в §03 кейса.
- В README нужно описать: код адаптера, схему результатов, соответствие наших четырёх `type` типам ошибок из кейса, рабочую папку и команду запуска в контейнере.

### Формы ответов

| Что | Форма |
|---|---|
| Первое наблюдение | `{"task": str, "manifest": object, "policy": object, "remaining_steps": 100}` |
| Остальные наблюдения | `{"result": value_or_null, "error": null_or_object, "remaining_steps": int}` |
| Ошибка | Публичный код и короткий текст. Без путей, seed и закрытых данных |
| `list_records` | `{"records": [object], "next_cursor": null_or_string}` |
| `get_record`, `get_document` | Объект записи или документа |
| `calculator` | Десятичная строка |
| `submit` | Только `{"accepted": true}` или ограниченная ошибка структуры. Никакой оценки правильности |

### Граница доступа

- `generate_episode`, пути, seed, config, truth, provenance и `score_episode` остаются у жюри.
- Политика работает в отдельном ограниченном процессе. Она получает только наблюдения и результат `step`, не импортирует оценщик и не видит папку эпизода.
- Спрятать поля в Python-объекте — не изоляция.
- В закрытом режиме `reward` для политики всегда 0, включая последний шаг. В `train` итоговая награда политике доступна.
- Oracle жюри строит ответ из закрытого truth на своей стороне и отправляет его обычным `submit`.

### Пограничные правила

- `submit` — одно из 100 действий, но в `inspection_steps` не входит. Все вызовы `step` до него, включая ошибочные, входят.
- `submit` сотым действием принимается. 100 действий без `submit` — `truncated`.
- 60 секунд на эпизод: от начала `reset` до конца, вместе со временем политики. При превышении жюри останавливает прогон и считает ответ пустым.
- JSON сравнивают по значениям. Порядок ключей и пробелы не важны, порядок списков важен (кроме объявленных множеств).

### Фикстуры жюри

Все загружаются через `episode_dir`. Значит, среда и оценщик должны работать на папке, которую жюри могло собрать или поправить само.

- **C** — чистый эпизод с известными записью R1 и документом D1.
- **E** — эпизод с одной ошибкой и полным набором доказательств.
- **L** — эпизод с таблицей не меньше 101 записи (три страницы).
- **U** — ID, которого точно нет в открытых данных.

## 3. Блок 2: данные и эталон, D01–D20 (25 баллов)

Эпизоды создаёт **наш** генератор через **наши документированные настройки**. Если тип ошибки нельзя включить отдельно, это засчитают как отсутствие независимой настройки.

| Эпизоды | Сценарий |
|---|---|
| D01 | Чистая компания, обычная сверка |
| D02 | Чистая, с корректно разбитым платежом |
| D03 | Чистая, с корректным возвратом |
| D04 | Чистая, с законными повторяющимися суммами |
| D05 | Чистая, с корректным случаем на валютной или периодной границе по policy |
| D06–D08 | Дубль счёта (разные ID, суммы, документы) |
| D09–D11 | Платёж без распределения или с частичным; нужен хотя бы один случай каждого вида |
| D12–D13 | Неверная дата или курс конвертации |
| D14–D15 | Ошибка периода |
| D16–D18 | Наш первый сценарий взаимодействия, с разными параметрами |
| D19–D20 | Наш второй сценарий взаимодействия |

Эпизод засчитан, только если выполнено всё:

1. До внесения ошибки книги сходятся. Это должно проверяться независимо по `provenance.json` и исходным документам. Формат provenance документируем мы.
2. Внесённое изменение создаёт именно заявленное расхождение. Проверяют по состоянию «до» и «после», не через наш matcher.
3. `type`, `affected_ids`, сумма и валюта в truth соответствуют реальному изменению. В чистом эпизоде truth пуст.
4. Хотя бы один полный набор доказательств доступен через инструменты, и по нему вывод проверяется без truth.
5. Форматы §03 соблюдены: время со смещением, деньги в минимальных единицах, курсы строками, явные `null`. Лишние документированные поля разрешены, если не выдают эталон.
6. Нет противоречивых и неразрешимых данных.

Отдельно сказано: то, что наш matcher принял наш oracle, корректность не доказывает. Жюри сверяет по нашим документированным проводкам и policy.

## 4. Блок 3: matcher и награда, тесты 1–20 (25 баллов)

Фикстура: одна ошибка A типа T, запись R1, сумма 10000 KZT, набор доказательств {D1, D2}, допуск **τ = 0**. Правильный вывод F совпадает с A по всем полям. В unit-тестах `inspection_steps = 10`, если не сказано иное.

| 13 | Ошибки A и B; верный вывод только для A | 1 / 0 / 1 | 2/3 | 47/150 |

## 5. Блок 4: парные проверки, P01–P20 (15 баллов)

Жюри один раз вызывает `generate_episode`, делает **копию папки**, сама переставляет записи и меняет ID (в том числе в truth и provenance) и подаёт обе папки через `episode_dir`. От нас переключатель преобразования не нужен.

| Пары | На каких эпизодах | Преобразование |
|---|---|---|
| P01–P05 | D01–D05 | Перестановка записей |
| P06–P10 | D06–D10 | Замена ID |
| P11–P20 | D11–D20 | И то и другое |

Что меняют: `row_id`, `doc_id`, `invoice_id`, `payment_id`, `entity_id`, `affected_ids`, `evidence_ids` и все ссылки на них. Разные пространства ID заменяются отдельно. Порядок `line_items` не трогают. Ключ курса вида `date:source_currency:target_currency` считается естественным ключом и не меняется. Наши дополнительные поля со ссылками тоже нужно менять, поэтому их надо перечислить в документации.

Пара засчитана, если:

1. На исходном эпизоде повтор тех же seed, config и действий точно воспроизводит записи, переходы и награды. `reset` не тянет состояние прошлого эпизода.
2. На преобразованном эпизоде oracle сдаёт те же выводы с новыми ID. После обратной замены ID совпадают типы, записи, суммы, валюты и доказательства.
3. TP, FP, FN, P, R, F1 и награда совпадают при одинаковом `inspection_steps`.
4. Не появилось утечки или недоступного доказательства.

Побайтовое совпадение файлов не требуют. От произвольной политики не требуют тех же действий после замены ID.

## 6. Инженерия (10 баллов)

| Критерий | Что нужно на 2 балла |
|---|---|
| Одна команда | Документированная команда запускает проверку без скрытых ручных шагов |
| Версии конфигураций | Сохранены версии кода, зависимостей и config, параметров хватает для повтора |
| Траектории | `trajectories.jsonl` с полями из §09, шаги прослеживаются, эталона в наблюдениях нет |
| Измеренный разбор сбоев | Показан измеренный сбой, его причина и повторная проверка после исправления (или воспроизводимый неустранённый предел) |
| Честные ограничения | Ограничения привязаны к проверяемым сценариям; нет заявлений об улучшении обучения без сравнения |

Утечка, запись в оценщик, реальные финансовые данные или неработающее ядро блокируют оценивание целиком.

## 7. Точные правила matcher

- **ID** сравниваются как строки, точно, с учётом регистра и пробелов. Ничего не обрезаем, не приводим типы, не ищем похожие.
- **`affected_ids`** — множество. Порядок и повторы внутри списка не важны. Должно точно совпасть с каноническим набором ошибки. Канонические правила по типам публикуем в коде matcher заранее.
- **`evidence_ids`** — множество, но лимит 10 проверяется **до** удаления повторов. Нужен целиком хотя бы один допустимый набор. Лишние существующие ID разрешены. Несуществующий или недоступный ID — вывод не сопоставляется (FP).
- **`type`** — точное совпадение с нашим документированным значением. Неизвестная строка — это FP, а не ошибка структуры.
- **`currency`** — точное совпадение, без смены регистра и обрезки пробелов.
- **`claimed_amount_minor`** — целое число JSON. Строка, дробное или `true`/`false` — ошибка структуры.
- **Порядок проверки:** сначала структура и размеры, потом нормализация множеств. 31 вывод, 11 ID доказательств или `explanation` длиннее 1000 символов — ошибка структуры всего `submit`, награда −1. Длина считается в символах Unicode (code points).
- **Структура против несовпадения:** неверный тип значения, отсутствующее обязательное поле, превышение лимита — ошибка структуры. Структурно верный вывод с неправильным содержимым — просто FP.
- **Допуск суммы:** по умолчанию τ = 0. Для отдельного типа можно заранее опубликовать фиксированное целое τ ≥ 0 в policy или в документации matcher. Условие: `abs(claimed − expected) ≤ τ`.
- **Сопоставление:** двудольный граф «выводы — ошибки», повторы — отдельные вершины. Берём паросочетание наибольшего размера. TP — его размер, FP — выводы минус TP, FN — ошибки минус TP.
- **Выбор среди равных:** `issue_id` сортируются по code points; берётся лексикографически наименьшая отсортированная последовательность пар `(issue_id, индекс вывода с 0)`. На TP/FP/FN и награду это не влияет.
- `explanation` в сопоставлении не участвует.

### Примеры M01–M12

Ошибка A: `affected_ids = {R1, R2}`, 10000 KZT, доказательства {D1, D2}, τ = 0. D3 существует, U не существует.

| ID | Вход | Результат |
|---|---|---|
| M01 | `affected_ids = [R2, R1, R1]` | Множество равно {R1, R2}, вывод может быть TP |
| M02 | `affected_ids = [R1, R2, R3]`, R3 существует, но не затронут | FP = 1, FN = 1 |
| M03 | `evidence_ids = [D2, D1, D3]` | Набор включён, вывод может быть TP |
| M04 | `evidence_ids = [D1, D2, U]` | FP = 1, FN = 1, хотя минимальный набор есть |
| M05 | 11 ID доказательств, 10 из них — повторы D1 | Ошибка структуры, награда −1 |
| M06 | Валюта отличается регистром или пробелом | FP = 1, FN = 1 |
| M07 | Сумма 10001 при τ = 0 | FP = 1, FN = 1 |
| M08 | Отдельная фикстура с τ = 1: сумма 10001 | Может быть TP; 10002 уже нет |
| M09 | Сумма строкой `"10000"` или `true` | Ошибка структуры, награда −1 |
| M10 | Ошибки A и B; F0 подходит обеим, F1 только A | F1→A, F0→B; TP = 2. Жадный выбор F0→A недопустим |
| M11 | A и B; F0 и F1 подходят обеим | TP = 2; пары A→F0, B→F1 |
| M12 | A; два одинаковых верных вывода | TP = 1, FP = 1 |
